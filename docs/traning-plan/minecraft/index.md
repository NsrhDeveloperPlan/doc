# Minecraft 模组开发学习路线

玩过 Minecraft 的你，应该接触过不少模组（Mod）：新的矿石、武器、机器、生物，甚至完全不同的游戏机制。

平时安装模组，我们只需要下载文件、放进对应的文件夹，再启动游戏。而开发模组，就是自己编写代码、制作资源，让这些新内容真正成为游戏的一部分。

比如，你可以让游戏出现一种原本不存在的矿石，用它制作特殊武器；也可以设计一台机器，让它消耗材料、积累能量，再产出新的物品。

这些功能背后涉及 Java 编程、游戏接口、资源文件、数据保存等知识。

如果你熟悉 Minecraft 的基本玩法，但还没接触过编程，也可以从这条路线开始。我们会先用六周学习必要的 Java 基础，再进入真正的模组工程。

整条路线共 24 个学习周，加上 2 个缓冲周，总计 26 周。每周预计投入 5～7 小时。这个时间是课程规划预算，并不意味着所有人都能在固定时间内完成全部任务。

你不需要先完成前端或后端路线，也不需要提前学完一整本 Java 教材。

## 一、半年围绕同一个模组做什么

这条路线的最终作品叫做：

**星辉工坊（Starlight Workshop）**

它是一个围绕星辉材料、装备、机器与特殊生物展开的综合模组。

我们会从最简单的自定义物品开始，逐步让游戏中的内容关联起来。

**第一步：让新物品出现在游戏中**

从一颗“星辉水晶”开始，学习物品注册、贴图、名称、方块、配方与掉落机制，逐步制作工具和装备。

**第二步：让物品有实际用途**

制作充能台，设计材料输入、处理进度和产物输出，让已有物品形成完整的游戏机制。

**第三步：让模组拥有自己的生物**

使用 Blockbench 制作模型，逐步加入属性、行为和交互，让“星辉小精灵”能够在游戏中被召唤、驯服并跟随玩家。

**第四步：让这些内容融入生存世界**

加入自然生成的星辉矿脉、探索进度和配方兼容，最后整理、打包并准备公开发布。

整条路线有一个重要原则：从第 7 周开始，每周都在已有的“星辉工坊”工程上继续增加内容，不反复创建互不相关的新模组。

到最后，你应该能够解释自己的代码如何工作，独立构建模组文件，在匹配的游戏环境中运行，并准备好申请公开发布所需的材料。

我们的目标不是“半年精通 Java 和 Minecraft 底层”，而是完成一个自己真正理解的作品。

## 二、为什么前六周先学 Java

本路线使用 Java 开发 Minecraft Java 版模组。

你以后看到的物品、方块、实体和交互逻辑，大多需要通过 Java 代码组织。

如果一开始就进入完整的模组工程，可能会同时遇到很多问题：代码看不懂、依赖下载失败、不知道报错在哪里，甚至分不清 Java 语法错误和 Minecraft 接口错误。

因此，前六周先用控制台程序熟悉 Java。

所谓控制台程序，就是在终端里运行、通过文字输入和输出结果的程序。它不需要启动 Minecraft，也不需要制作图形界面。

我们会用熟悉的游戏机制练习编程。

| Java 知识 | 在控制台中练习 | 后续模组开发中的用途 |
| --- | --- | --- |
| 变量、数据类型、条件判断 | 计算生命值与伤害 | 判断物品状态和使用条件 |
| 循环、List、Map | 管理九格快捷栏 | 理解物品集合与存储逻辑 |
| 类、对象、常量 | 编写 Item、Weapon | 组织物品和实体代码 |
| 继承、多态 | Zombie、Creeper | 理解不同实体的行为 |
| 接口、枚举、泛型 | 物品稀有度与注册表 | 理解类型约束及注册思想 |
| Lambda、方法引用、JSON | 改造注册表与读取数据 | 理解工厂方法、数据文件与构建配置 |

这些知识不需要一次全部学会。

例如，第 1 周只需要使用变量和 `if-else` 做一个简化伤害计算器。第 4 周再通过不同生物的攻击方式理解多态。

每周学到的内容，都要用在当周的练习程序中。只看完教学视频，没有运行成果，不算完成。

::: tip 前六周的代码会变成真正的模组吗？
不会直接转换。

前六周编写的是用于理解 Java 的独立控制台练习；第 7 周会使用模组开发模板建立新的工程。

你可以在同一个学习仓库中保存两个阶段的代码与记录，但不必强行把控制台背包、模拟实体等练习代码全部搬进模组。

真正需要带过去的是你对 Java 语法、对象组织和程序运行过程的理解。
:::

### Java 基础还可以用在哪里

如果以后还想学习 Java 后端，前六周积累的 Java 语言知识也能继续使用。

例如，类与对象、泛型、集合、Lambda、Git 和 Gradle 的相关经验，都具有一定的复用价值。

但 Minecraft 模组与 Java 后端使用的框架、接口和业务逻辑并不相同。

你可以在完成模组方向后，再考虑 [Java 后端开发学习路线](../backend/index.md)，不需要同时学习两套完整课程，也不要把两个方向都算进这 26 周里。

## 三、开始前要认识的工具和版本

模组开发除了编写 Java，还需要一个能让代码与 Minecraft 协同工作的开发环境。

这里先认识几个必要概念，不要求现在把所有工具一次装齐。

### Minecraft Java 版与基岩版

Minecraft 主要有两个常见版本：

- Java Edition（Java 版）：本路线的开发目标，主要使用 Java 及对应的模组开发生态。
- Bedrock Edition（基岩版）：有自己的附加包、脚本和扩展体系，开发方式与本课程不同。

本课程中的 Fabric、NeoForge、Java 模组工程等内容，都面向 Minecraft Java 版。

如果你平时玩的是基岩版，需要先确认自己是否具备使用 Java 版的条件。不能直接把本路线构建出来的 Java 模组安装进基岩版。

### JDK、IDE 与 Gradle 分别是什么

刚开始可能会看到一串陌生名称，先弄清楚分工就够了。

| 工具 | 负责什么 |
| --- | --- |
| Java | 我们主要使用的编程语言 |
| JDK（Java Development Kit） | Java 开发工具包，提供编译器等开发工具 |
| IDE（集成开发环境） | 编写、运行、调试代码的软件 |
| Gradle | 管理项目依赖、编译和构建任务的工具 |
| 模组加载器 | 让模组能够在对应的 Minecraft 环境中被加载，并提供相应的开发机制 |

本课程推荐使用 IntelliJ IDEA 作为主要 Java 开发工具。它能帮助我们阅读代码、定位错误、管理项目和调试程序。

不过，IDE 只是工具，安装 IDEA 并不等于已经拥有完整的模组开发环境。

Gradle 则负责处理项目构建和依赖。模组模板通常会附带 Gradle Wrapper，它能够使用工程指定的 Gradle 版本，因此一般不需要另外安装全局 Gradle。

第 6 周会初步接触 Gradle，第 7 周再正式使用模组开发工程。

### Fabric 和 NeoForge 怎么选

Minecraft Java 版有不同的模组加载器和开发生态。

本路线考虑两种：**Fabric 和 NeoForge**。

两者都可以用于开发 Minecraft 模组，但它们的开发 API、工程配置和使用的生态工具存在差异。

| 比较项 | Fabric | NeoForge |
| --- | --- | --- |
| 官方文档 | 提供英文及部分中文翻译，具体内容因版本而异 | 主要以英文文档为主 |
| 开发方式 | 使用 Fabric Loader、Loom 等工具，按需引入 Fabric API | 使用 NeoForge 开发生态及对应 Gradle 插件 |
| 项目初始化 | 可以通过官方模板生成器创建项目 | 可以通过官方提供的开发模板或项目生成方式创建 |
| 学习时应考虑 | 所选游戏版本的文档是否完整，所需 API 和库是否可用 | 所选游戏版本的文档是否完整，所需功能与第三方兼容是否满足 |
| 官方资料 | [Fabric 中文开发文档](https://docs.fabricmc.net/zh_cn/develop/) | [NeoForge 开发文档](https://docs.neoforged.net/) |

两种方案都可以用于实现本课程的主要目标，但具体实现方式不能直接混用；第三方库和兼容功能还需要按选定版本逐项确认。

另外，Fabric Loader 和 Fabric API 不是同一个东西。

Fabric Loader 主要承担模组加载、初始化和相关基础功能；Fabric API 是单独提供的一组游戏相关接口与功能支持。是否需要引入 Fabric API、需要哪些模块及版本，应根据当前项目和对应版本的文档确定。

NeoForge 也有自己的开发接口和依赖配置。

所以看到某篇教程里的 Java 类名与你正在使用的很像，也不能直接认定代码通用。

### 为什么必须统一游戏版本

Minecraft 会持续更新。

有些更新只改变游戏内容，有些更新会调整类名、方法、数据格式或渲染机制。这些变化都可能影响模组开发。

因此，学习时至少要确认：

**Minecraft 游戏版本 + 加载器及其版本 + 对应版本的主教程**

同时，还需要记录：

- JDK 版本。
- Gradle Wrapper 使用的 Gradle 版本。
- 对应的开发插件及必要依赖版本。

这几项应该相互匹配。

例如，你正在用某个版本的 NeoForge 开发，就不能直接照抄另一个 Minecraft 版本的 Fabric 教程，然后认为只需要修改导入语句就能运行。

第 6 周结束前，我们会确定实际使用的版本组合，并记录到项目 README 中。第 7～24 周以这套组合为基线。

这并不是说以后永远不能升级。只是学习阶段先把功能做出来，避免同时承担学习新知识和迁移旧代码两种成本。

### 已核对的版本信息

官方资料核对日期：2026 年 11 月 12 日。

原始课程大纲曾列出 Minecraft 26.1.x 与 JDK 25、Minecraft 1.21.1 与 JDK 21 等候选组合。

通过官方资料可以确认以下关系：

| Minecraft 版本 | 已确认的 Java 要求 | 核对依据 |
| --- | --- | --- |
| 1.21.1 | 开发使用 JDK 21 | [Fabric 1.21.1 开发环境](https://docs.fabricmc.net/1.21.1/develop/getting-started/setting-up-a-development-environment)、[NeoForge 1.21.1 入门文档](https://docs.neoforged.net/docs/1.21.1/gettingstarted/) |
| 26.1 | 游戏要求 Java 25；Fabric 开发的 Gradle JVM 至少使用 Java 25 | [Minecraft 26.1 官方更新说明](https://www.minecraft.net/en-us/article/minecraft-java-edition-26-1)、[Fabric 26.1 开发说明](https://fabricmc.net/2026/03/14/261.html) |

这些信息确认的是相应游戏版本的 Java 要求，不等于已经确认了一套完整的课程开发环境。

例如，Fabric 官方在 2026 年 3 月的 26.1 开发说明中还给出了当时的 Loom 与 Gradle 版本建议。这类建议需要结合实际生成的项目重新核对，不能直接当成长期固定的配置。

具体的加载器版本、开发插件、Gradle Wrapper 版本、模板与教学文档组合，将在第 6 周确认，并由第 7 周的模组工程实际验证。

本页不提前指定 Fabric 或 NeoForge 中的某一套作为唯一课程环境。

::: warning 不要混用不同版本的教程
如果代码报错，先检查游戏版本、加载器、JDK 和教程版本是否一致，再考虑代码本身的问题。

特别是注册方式、资源文件格式、模型、实体和 GUI 等内容，跨版本变化可能比较明显。不要把不同版本的代码片段直接拼在一起。
:::

## 四、24 周学习任务索引

整个课程分为四个阶段，每阶段六个学习周。

| 阶段 | 周次 | 阶段目标 |
| --- | --- | --- |
| Java 预热 | 第 1～6 周 | 掌握常用 Java 语法与工程基础 |
| 物品与装备 | 第 7～12 周 | 让星辉工坊具备基础生存玩法 |
| 模型与机器 | 第 13～18 周 | 加入数据生成、功能机器和特殊生物 |
| 世界与发布 | 第 19～24 周 | 完善玩法、兼容性并准备公开发布 |

第 12 周后和第 18 周后分别安排一个缓冲周，不计入 24 个核心学习周。

下面的任务表就是本路线的长期进度索引。每一周的具体操作、代码和排错方法，会在对应的独立教程中展开。

### 第一阶段：Java 预热（第 1～6 周）

这一阶段不启动 Minecraft，通过控制台练习模拟一些简化的游戏机制。

| 周次 | 本周学什么 | 必做成果 | 选做或提醒 |
| --- | --- | --- | --- |
| [第 1 周](./week-01.md) | 开发环境、基本数据类型、变量、`if-else` | 完成控制台“史蒂夫属性面板与伤害计算器”，进行首次本地 Git 提交 | 伤害计算采用教学简化规则，不完整复现原版公式 |
| 第 2 周 | 循环、数组、`List`、`Map` | 编写九格快捷栏背包，支持添加、堆叠和检索物品 | 选做：迷你合成表。练习统一以 64 为堆叠上限，不代表所有原版物品都能堆叠 64 个 |
| 第 3 周 | 类与对象、`static`、`final`、异常堆栈 | 编写 `Item` 和 `Weapon` 类，让不同武器拥有独立耐久，攻击时扣除耐久，并使用静态常量登记固定值 | 在受控练习中主动制造一次空指针异常，学会从堆栈定位代码位置 |
| 第 4 周 | 继承、多态、抽象类、`@Override` | 编写 `Entity` 抽象父类与 `Zombie`、`Creeper` 子类，通过统一集合调用不同攻击逻辑 | 无 |
| 第 5 周 | 接口、枚举、泛型 | 创建武器稀有度枚举与 `SimpleRegistry<T>` 简化注册表 | 这里只练注册思想，不代表真实加载器的注册 API |
| 第 6 周 | Lambda、方法引用、JSON、Gradle 基础 | 使用 `Supplier<T>` 改造注册表，运行一个 Gradle 项目，并将选定的版本组合写入 README | 选做：使用 Gson 读取 JSON、使用 `record` 定义数据模型 |

第 6 周结束时，需要确认自己已经能够：

- 阅读基础 Java 类和方法。
- 理解对象、集合、继承、接口和泛型的用途。
- 根据异常信息找到出错位置。
- 知道 Gradle 项目的基本作用。
- 确定并记录后续模组工程的版本组合。

这时，进入游戏所需要的基本 Java 知识就有了。

### 第二阶段：进入游戏，建立物品与装备体系（第 7～12 周）

从第 7 周开始，正式创建 Starlight Workshop 模组工程。

这一阶段的目标是让新的材料能够被找到、加工和使用，形成最基本的生存玩法。

| 周次 | 本周学什么 | 必做成果 | 选做或提醒 |
| --- | --- | --- | --- |
| 第 7 周 | 使用官方模板建立模组工程、注册物品 | 在开发客户端获得自绘贴图的“星辉水晶”，配置中文和英文名称 | 确保游戏、加载器和模板版本匹配 |
| 第 8 周 | 自定义方块、挖掘相关标签、创造模式物品栏 | 制作深层星辉矿石、发光装饰方块和星辉工坊专属物品栏 | 无 |
| 第 9 周 | 手写配方与战利品表 JSON | 实现合成、熔炼和挖矿掉落，形成材料获取与使用的生存闭环 | 选做：精准采集与时运对掉落的影响 |
| 第 10 周 | 工具、武器、食物 | 制作星辉工具套装，以及食用后附带状态效果的“星辉果实” | 无 |
| 第 11 周 | 右键交互、冷却机制、客户端与服务端职责 | 实现传送法杖和探矿杖 | 选做：用数据组件记录充能。改变世界的逻辑应由服务端负责 |
| 第 12 周 | 盔甲、音效、套装效果与打包 | 完成基础装备里程碑版本，在独立测试客户端中验证构建产物及所需依赖 | 选做：自定义状态效果 |

到第 12 周，你应该已经拥有一个能够实际游玩的基础模组。

玩家可以在游戏里获取星辉材料，再通过加工和制作，得到不同用途的物品和装备。此时可以先通过配方获取材料；自然生成的矿脉安排在第 20 周。

这里要注意一个后面会反复出现的概念：客户端与服务端的职责不同。

客户端主要负责画面、音效和交互展示；服务端负责需要保持一致的游戏规则与世界状态。

即使你只在单人游戏中测试，也要开始理解这一区别。尤其是传送、物品消耗等行为，不能只在客户端自行修改世界状态。

**缓冲周 A：第 12 周之后**

这一周暂时不增加新功能。

优先补齐第 7～12 周未完成的必做内容，再检查：

- 中文和英文物品名称是否正常。
- 配方、掉落和装备功能是否符合预期。
- 模组是否能够在独立测试环境中运行。
- 是否保留了可用的构建产物和周志。

最后录制一段简短的实机演示，记录这一阶段的成果。

### 第三阶段：数据生成、模型与机器（第 13～18 周）

前面已经可以添加物品、方块和装备。

这一阶段开始解决更复杂的问题：如何减少重复资源配置、如何制作特殊模型，以及怎样让一个方块保存数据并持续处理物品。

我们会制作星辉工匠台、充能台和星辉小精灵。

| 周次 | 本周学什么 | 必做成果 | 选做或提醒 |
| --- | --- | --- | --- |
| 第 13 周 | Datagen 数据生成 | 使用程序生成已有资源和配方，并扩展建筑方块 | 先核对生成结果，再替换手写资源，避免重复或遗漏 |
| 第 14 周 | Blockbench、异形方块模型 | 制作立体武器模型和星辉工匠台，并考虑碰撞与遮挡 | 无 |
| 第 15 周 | 方块实体、物品存储、计时与持久化 | 实现充能台的底层逻辑，退出游戏再进入后数据仍能有效保存 | 具体保存接口和方法以选定版本为准 |
| 第 16 周 | 容器菜单、界面、槽位和进度同步 | 完成带输入槽、输出槽和进度条的充能台，投入材料后产出强化合金 | 服务端处理加工规则，客户端负责显示 |
| 第 17 周 | 自定义配方类型与序列化 | 将充能台配方改为数据驱动，使其能够通过数据包扩展 | 无 |
| 第 18 周 | 自定义生物、模型、属性和刷怪蛋 | 制作“星辉小精灵”，能通过刷怪蛋在游戏中召唤 | 选做：基础动画。动画库必须符合当前版本的兼容要求 |

这里有几个新的概念值得提前认识。

**Datagen（数据生成）**，就是通过程序批量生成资源或数据文件。比如有很多结构相似的方块和配方时，可以减少重复手写 JSON 的工作。

**Blockbench** 是用于制作 Minecraft 风格模型的工具。第 14 周开始，我们会用它处理不再只是简单方块或物品贴图的模型。

**方块实体（Block Entity）** 则用于处理需要保存额外状态的方块，例如充能台内部的物品、剩余加工时间等。

这部分会涉及较多新的类、数据格式和游戏机制，不必强求一次理解所有内容。

尤其是第 15～17 周的机器开发，要按顺序推进：

先让数据能保存，再让机器能处理材料，最后再把加工规则改为可扩展的配方系统。

**缓冲周 B：第 18 周之后**

这一周主要整理第 13～18 周的成果。

补齐尚未完成的必做功能，清理重复代码，按职责整理包结构。

然后创建一个新的测试存档，从材料获取开始检查完整的生存流程，确认配方、机器和产物能够正常衔接。

不要直接拿自己的重要生存存档做实验。

### 第四阶段：行为、世界生成与发布（第 19～24 周）

最后六周，我们要让星辉工坊的内容进一步融入 Minecraft，并整理成能够交付给其他玩家使用的模组。

| 周次 | 本周学什么 | 必做成果 | 选做或提醒 |
| --- | --- | --- | --- |
| 第 19 周 | 生物 AI 目标、驯服与跟随 | 让星辉小精灵可以被驯服、跟随玩家，并提供一种辅助效果 | 无 |
| 第 20 周 | 矿脉与世界生成 | 让星辉矿脉能够在新存档中自然生成 | 选做：发光树和树苗 |
| 第 21 周 | 粒子、进度与附魔 | 制作引导玩家探索模组内容的进度树，并为已有交互加入一种星尘粒子效果 | 选做：专属附魔。具体资源格式以所选版本为准 |
| 第 22 周 | Mixin 与最小侵入原则 | 先使用已有 API 或自身方法实现一个功能，再练习一处确实适合注入的受控小改动 | 优先使用数据驱动、事件与现有 API，不为使用 Mixin 而使用 Mixin |
| 第 23 周 | 配方查看器兼容与配置 | 适配一个兼容当前版本的配方查看器，使其能显示充能台配方；开放冷却、距离或速度等配置 | 选做：第二个查看器兼容、游戏内配置界面 |
| 第 24 周 | 打包、README、许可证、截图、更新日志和发布申请 | 准备 GitHub Releases 与 Modrinth 发布资料，说明功能、依赖、安装方法、兼容版本和已知问题 | 选做：其他平台或中文社区介绍。审核结果和时间不作保证 |

第 22 周会接触 Mixin。

它是一种在指定位置向已有代码注入行为的技术，适合处理某些现有接口无法满足的需求。

但 Mixin 也会带来兼容性和维护成本。

因此我们会先学习使用已有 API、事件机制和数据驱动方式解决问题，确认确实需要注入后，再做一处范围明确的练习。

第 23 周的配方查看器兼容，也需要根据当时实际选定的游戏和加载器版本选择。

配置文件适合管理冷却时间、距离、处理速度等参数。但世界生成相关调整，应优先遵循当前版本的数据包及相关注册机制，不能假设所有游戏内容都能通过普通配置文件修改。

最后一周，我们会整理发布材料。

包括功能介绍、安装方法、所需依赖、兼容版本、许可证、更新日志和真实游戏截图。

GitHub Releases 可以作为版本构建产物的发布位置；Modrinth 则需要按照平台的现行规则提交项目并接受审核。

公开发布不只需要程序能运行，还需要确认素材来源、第三方依赖、许可证与平台内容规则。

发布前请阅读 [Modrinth 官方规则](https://modrinth.com/legal/rules)，尤其是在使用第三方素材或 AI 辅助内容时，按当时有效的要求处理。课程不保证审核结果或通过时间。

## 五、每周怎么学，怎样才算完成

本课程按每周 5～7 小时安排学习预算。

可以把时间分成三次使用：

| 学习安排 | 参考时长 | 主要任务 |
| --- | --- | --- |
| 第一次 | 约 2 小时 | 学习本周必要概念，阅读对应教程 |
| 第二次 | 约 2～3 小时 | 在当周项目中实现必做功能 |
| 第三次 | 约 1～2 小时 | 调试、验证、Git 提交、记录周志和截图 |

不用严格限制每次学习的时间，但建议保留这样的节奏。

### 每周的完成标准

我们会把每周任务分成两档。

必做是这一周需要达到的成果，选做是在基础任务完成后供有余力的同学继续练习的内容。

每周至少留下四样东西：

- **能运行的成果**：控制台程序能完成指定操作，或者模组功能能在对应游戏环境中验证。
- **Git 提交**：将本周完成的代码和必要资源记录到本地仓库。
- **简短周志**：在 `CHANGELOG.md` 中记录本周做了什么、解决了什么问题。
- **截图或动图**：保留一份能够展示实际运行结果的证据。

Git 是一种版本管理工具，能够记录项目在不同时间的变化。

第一次本地提交不要求登录 GitHub。前期只需管理好本地代码，对外发布时再处理远程仓库和相关账号。

`CHANGELOG.md` 也不用写得很复杂。

例如，完成第 7 周时，可以记录：

> v0.1：创建星辉工坊模组工程，添加星辉水晶，完成中英文名称和贴图配置，并在开发客户端中验证物品显示。

以实际完成情况为准，不要把计划做但没有做成的功能写成已经完成。

到了第 24 周，这些提交、周志和截图就能够帮助你整理作品的开发过程。

### 遇到复杂任务，可以先缩小范围

24 周任务表描述的是阶段目标，并不保证每个任务都能在 5～7 小时内完成。

尤其是以下内容，可能需要额外时间：

- 第 15～17 周：机器的数据保存、界面同步和自定义配方。
- 第 18～19 周：自定义生物模型与行为。
- 第 20 周：世界生成。
- 第 23 周：第三方模组兼容。

如果某周推进困难，先保证最小功能能运行。

例如，充能台可以先实现固定输入材料和一种产物，再逐步加入复杂配方；自定义生物可以先完成实体注册、模型和召唤，再完善动画与行为。

缩小实现范围是为了逐步达到必做目标，不能将尚未完成的功能直接算作通过。

如果连续两周都没有完成必做内容，建议暂停所有选做任务，优先补齐基础功能并主动求助。

第 12 周后和第 18 周后的缓冲周就是为这种情况预留的，不要为了赶进度而跳过 Git 提交、运行验证和周志。

## 六、遇到问题时，先检查什么

模组开发的报错有时比较长，尤其是 Gradle 依赖、Java 异常和游戏启动日志。

遇到问题时，可以按下面的顺序检查。

### 先看版本，再看代码

先确认自己实际使用的 Minecraft 版本、加载器及其版本、JDK、Gradle 和教程版本。

如果错误出现在依赖加载、类或方法不存在等位置，版本不匹配就是需要优先排查的原因之一。

不要直接把 AI 或其他教程提供的代码复制进工程。

尤其是模组 API，不同游戏版本和加载器下的实现方式可能不同。

### 卡住约 30 分钟就求助

可以先自己尝试排查，但不建议对同一个错误反复猜测几个小时。

提问时尽量提供：

1. 当前游戏版本、加载器及版本、JDK 版本。
2. 完整的关键报错和必要日志。
3. 出问题的代码或操作步骤。
4. 自己已经尝试过的解决方法。

注意在分享日志前检查个人路径、账号或其他敏感信息。

解决之后，可以将错误原因和处理过程写进自己的 `踩坑笔记.md`。

### Gradle 同步慢，不一定是代码的问题

第一次导入模组工程时，Gradle 可能需要下载大量依赖，包括对应版本的 Minecraft 开发资源。

因此第一次同步可能比较慢。

但也不能把长时间等待都视为正常。

要结合终端日志和下载进度判断。如果持续出现网络错误、依赖解析失败或异常堆栈，就应该根据具体错误排查。

不要在没有确认原因前反复删除缓存、重启同步或随意修改依赖版本。

### 使用独立测试存档

开发过程中可能会修改方块数据、实体行为和世界生成规则。

这些内容一旦出现错误，有可能影响存档。

因此我们始终建议使用独立的开发测试存档，必要时保留备份。

尤其是第 15 周开始处理持久化、第 20 周开始处理世界生成之后，更要注意不要拿重要存档直接测试。

### AI 可以辅助，但代码要自己理解

学习初期，可以让 AI 帮你解释 Java 概念、分析异常堆栈或说明一个方法的作用。

前两个阶段（第 1～12 周），项目代码自己编写；后两个阶段（第 13～24 周），可以让 AI 辅助生成样板代码，但提交前必须能够逐行解释。

使用 AI 代码时，还要检查它使用的游戏版本、加载器和 API，确认适用于自己的项目。

能复制代码让游戏启动，与能够独立维护一个模组，是两回事。

## 七、从哪里开始第一周

如果你已经决定走 Minecraft 模组开发方向，可以直接从本路线第 1 周开始。

本周的主题是：**Java 开发环境、变量、基本数据类型与条件判断**。

你要完成的第一个项目叫做：**史蒂夫属性面板与伤害计算器**。
